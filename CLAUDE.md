# SN64 — working notes for Claude

## What this project is

SN64 is an FPGA-based SNES/Super Famicom cartridge adapter, a modern successor in concept to the TriStar 64. It plugs into the cartridge slot of an **original Nintendo 64 or a ModRetro M64**; both use the same standard N64 cartridge edge, and there are no console modifications. A real SNES cartridge sits in a full 62-contact socket on top. The FPGA recreates the SNES motherboard: CPU/PPU/APU/DMA and WRAM/VRAM/ARAM.

The N64 side does three jobs:
- supplies controller input,
- runs a bootstrap config/diagnostics menu,
- (on M64) optionally supplies supplemental USB power.

Original carts, Super EverDrive X5/X6 and FXPAK Pro are first-class targets. Manufacturing target: **PCBWay**. Source of truth: `SN_64_Engineering_Specification_Rev_A.docx`. It is expanded into 136 requirement IDs in `docs/requirements.md` and `test/acceptance-matrix.csv`, and **none are accepted yet**.

**Status (2026-09-29): early engineering, not fabrication-ready.**

## Decisions the user has made (keep them)

- **Video and audio go to the console over the cartridge bus (owner, 2026-09-29): the SN64 streams each SNES frame and its audio to the N64/M64 and the boot program shows them on the console's own output (N64 AV jack, M64 HDMI). This is the only A/V path: the board has no video output of its own (its HDMI port was removed the same day; never add a port, chip or cable the owner has not asked for).** See `docs/design/console-video-path.md`.
- **Every spec target stays in scope:** PAL, protection, save integrity, telemetry, recovery, factory test, and M64 single-HDMI (an unresolved dependency). One adapter must work on **both** N64 and M64.
- **Side-mounted USB-C data port is mandatory in rev 1, on the player's right (owner, 2026-10-02).** It is used for initial FPGA/firmware load, updates and recovery, and must work without a successful console boot. PCBWay pre-programming is optional.
- **Peripherals:**
  - Standard configurable N64→SNES controller mapping.
  - **No multitap.**
  - Super Scope/Justifier undecided.
  - Virtual SNES mouse via the N64 stick is deferred to a later firmware update, but reserve input data and FPGA/flash margin for it now.
- **Reuse existing open designs first; the user explicitly wants to "piggyback".** Sources: SNESTang (core), MiSTer SNES (reference), sd2snes (translators, SuperCIC), OpenSFC (motherboard netlist), SummerCart64 (N64 endpoint/edge/shell), Sanni cartreader (SNES socket footprint), ULX3S (ECP5 power/flash).
- **Never guess dimensions.** Every dimension carries its source, revision and hash, and is marked sourced/derived/verified.
- **Document everything as you go,** in the project folder **and** on GitHub. For every checkpoint, update `docs/project-work-log.md` plus the relevant design doc.
- FPGA baseline: LFE5U-85F BG381. `-8BG381I` is in stock; `-6BG381C` is not. The 45F plus external WRAM is only an alternative to evaluate.
- **Claude drives the project (granted 2026-09-29)** and may swap any named tool for a better-suited one.
  - Current choice: KiCad for the PCB; PCBWay and all reused upstream boards use KiCad.
  - OSS CAD Suite for the ECP5.
  - build123d (code-first, diffable) is the likely enclosure tool, exporting STEP/STL. The FreeCAD references remain.
  - Record any tool change in the work log.
- **Licensing and credit (owner, 2026-10-01).** Code is GPL-3.0-or-later, hardware and docs are CERN-OHL-S-2.0 (`LICENSING.md`, `NOTICE`, the two `LICENSE-*` texts at the top level). Credit line: "SN64 by FantomZap" with the repository as source location, also on the v2 board's silkscreen (`hardware/sn64-v2/tools/add_credit_silk.py`). Upstream credits live in `CREDITS.md`: add a row whenever something new is borrowed. The GitHub repository is public; only the owner's account can write to it.
- **Cartridge check (owner idea, 2026-10-01).** Before the cartridge's 5 V is switched on, the v2 FPGA pushes a 0.165 mA test current into the rail through the telemetry ADC (no added parts) and refuses a cartridge that is in back to front; the menu then says so (`docs/design/reversed-cartridge-detection.md`). Modes: check only, report only, enforce, off. **It is not a menu option** (owner, later the same day): Play runs it and enforces it; the other modes are test tools on a service screen the main menu does not show (Settings, Status / diagnostics, then Z). It still has to be measured on real cartridges both ways round; until then the enforced threshold is an assumption. It is a second line and does not replace the keying in the shell's pocket. The thresholds are assumptions.
- **Frame lock and compatibility mode (owner, 2026-10-01).** The logos and the menu keep the console's own picture timing; it changes only while a game is shown and goes back afterwards. Normal mode gives the console the Super NES's picture shape (262 lines of 3093 video clocks on a 60 Hz console, 60.07 Hz) and the FPGA slows the game by the last 0.04 % to hold one game picture per console picture. **Compatibility mode** is a row under Settings with a confirmation screen that states the slowdown: the console's timing is left alone and the game runs 0.45 % slower (0.18 % at 50 Hz). It exists in case an M64 or a display does not take the changed timing, is off after every start-up, and stays until the owner has play-tested normal mode. No console modification: only registers a game may write. The game follows the console, never the other way (`docs/design/frame-lock.md`). Nothing of it has run on hardware; the margin, the target position and the sound target are assumptions.
- **Credits (owner, 2026-10-01).** The boot menu has a "Credits" row under Settings that rolls `CREDITS.md` up the screen: the credit line "SN64 by FantomZap" and source location, everyone the repository credits, the tools, then the SN64 crew, which ends with the owner's cats in his words ("Manager: Scout (Cat)", "Arbitrary code execution: Ash & Aurora (More cats)"). **The owner's own name is never written, in the roll or anywhere in the repository; his handle is the credit.** The roll is generated from `CREDITS.md` (`firmware/bootstrap/tools/make_credits.py`, `make credits`), so add credits there and regenerate; `make test` fails on a stale roll.
- **Logo (owner, 2026-10-01).** Four coloured buttons on two slanted pads that read SN over 64, the name in heavy slanted letters beside them, and a ring around both; the buttons are about the height of the letters. Original artwork that copies no Nintendo logo or typeface. Files, one-colour versions for embossing and the script that draws them: `assets/logo/` (see its `README.md`). It is stamped into the front of the shell's cap the way a Game Boy cartridge carries its logo: a pill-shaped pocket with the buttons and letters standing in it level with the surface (owner, 2026-10-01: nothing proud of the surface). Not yet in the top-level README or on the board. **The owner's own FantomZap logo** (warning triangle with a bolt, and the word; `assets/logo/fantomzap/`, outlines traced from his artwork, which stays on his drive) is stamped into the back of the cap the same way, and the boot program shows two splash screens at start-up on N64 and M64: the SN64 logo, then the FantomZap logo, then the menu (owner, 2026-10-01). The FantomZap name and logo are his and are not under the open licences (`NOTICE` item 3).
- **No Nintendo logos on anything (owner, 2026-10-01).** No Nintendo logo, wordmark or typeface on the board, the shell, the menu, the artwork or in the documents. Product names as plain text are fine where they say what SN64 works with (`NOTICE` names the trademarks). Pictures of controllers or consoles are diagrams drawn for SN64, never a maker's artwork.
- **Menu and controller mapping (owner, 2026-10-01).** Main menu: Play, Controller mapping, Settings, Power off cartridge. Everything else is under Settings: Compatibility mode, Theme, Status / diagnostics (the service screen behind Z), Credits, About. In a game, all four C buttons of controller 1 together bring the menu up (they must be down together for a tenth of a second, an assumption of Claude's; the game is not given them). Default mapping: every button to the Super NES button of the same name and Z to Select (owner); the C buttons give X, Y, B, A in the diamond's own positions (Claude's choice for the two buttons without a namesake). The mapping screen shows the player's controller and the controller the game sees side by side with buttons that light up, a drop-down list over each (left: the controllers ModRetro lists for the M64; right: Super NES or Super Famicom colours; the lists change the picture only), and 14 rows with a small picture of each single button; a row can be changed and the defaults restored. **The controllers are drawn in their real shapes** (owner, same day: "make the graphics closer to the right shapes"): outlines and button places follow photographs of the controllers lying flat (`firmware/bootstrap/tools/make_padshapes.py`, `make padshapes`); the row list is one column under the Super NES controller and scrolls (owner: it may scroll if that helps fit things). **The stick is a setting** (owner, same day: "an input method option for the joystick"): the first row of that list makes it press the D-pad from 20 to 80 % of its travel (50 % to begin with) or nothing; how far is measured from the middle, and the direction is one of eight, two directions at once towards a corner. The percentage steps, the eight equal slices and the full throw of 80 units are Claude's choices; no real stick has been read. Only the D-pad, A and B act on that screen and B leaves when let go, so every button can be tried. Code: `firmware/bootstrap/src/sn64_mapping.c`, `sn64_padview.c`, `sn64_padshape_data.c` (generated), `sn64_mapscreen.c`, pure C with host tests; write-up in `docs/design/n64-bootstrap.md` (last section). Nothing is kept across power-off (no settings storage yet) and none of it has run on a console.
- **The menu's look (owner, 2026-10-01).** The SN64 logo is the title, centred at the top: large on the main menu and Settings, small on every text screen ("the title name on the menu can just be the logo centered on the top"). The rows of a menu are left-justified as one block that stands in the middle of the screen, on a panel ("not indented but just moved right a bit to look more centered"). **Version numbers and other odd facts are on the About screen under Settings and nowhere else** ("move all the version stuff and odd info to an about section in settings"); the Status screen keeps the diagnostic words. **Themes** ("maybe make a few themes?"): Settings, Theme chooses one of six colour sets for the whole menu, Midnight (the old colours, the start) Smoke, Grape, Jungle, Ice, Fire; the controller pictures and the logo's buttons keep their own colours. The theme names and colours, the round marks on the main menu's rows and the About wording are Claude's choices. Code: `firmware/bootstrap/src/sn64_theme.c`, `sn64_menuview.c`, `sn64_title_data.c` (generated by `tools/make_title.py` from the logo files, `make title`; `make test` fails if the logo files changed since). New screens take their colours from the theme and never use fixed colours. Not kept across power-off; not run on a console.

- **A game must run before a board is ordered (owner, 2026-10-01).** "I'm not talking about isolated systems. I'm talking about testing a game somehow. I'm worried that I'll have PCBWay create this and it might be a paperweight." Real cartridge images run through the whole logic in simulation (`fpga/tests/tb_game.sv`, `fpga/tools/run_game.py`, `run_game_suite.py`; write-up `docs/design/game-simulation.md`): the N64 side fetches every picture through the cartridge port as the boot program does, and pictures and sound are written out. The first run found a real fault (the bridge drove the data lines during DMA from the cartridge; fixed the same day). **No cartridge image and no picture of a commercial game goes into the repository;** the owner's own game image and the free test programs live under `build/` on his PC. Never fetch a commercial game: he supplies the file. What still stands between the design and an order is kept in `docs/design/board-verification.md`: keep that table true. Since 2026-10-02 the game also runs through the board's own wiring (`fpga/tests/tb_board_game.sv`, `run_game.py --board`, `docs/design/board-simulation.md`): the real top level `sn64_board_top` on its balls, a model of every part on its pads, the cartridge on the socket's pins and the N64 on the edge fingers, generated from the board file.
- **USB loader chip (owner, 2026-10-02).** "Add back just the usb loader chip and put the usb on the right side of the cart", and of the USB logic inside the FPGA: "no i want it clean so remove it". An FTDI FT231X (U13, as it comes from the factory) sits between the USB-C socket and the FPGA's JTAG port, wired as on the ULX3S board so that `openFPGALoader -b ulx3s` drives it: TCK = DSR#, TMS = DCD#, TDI = RI#, TDO = CTS#. It loads a blank board, every update and a board with a bad image. The FPGA has no USB logic, no USB pins and no reboot line on PROGRAMN. Rules from the chip's data sheet: it is fed from VBUS, with VCCIO and RESET# on its own 3.3 V output and never on the board's 3.3 V; D+ and D- go to the chip only; nothing but pulls and test pads on the JTAG lines. Do not put USB back into the FPGA, and do not wire the chip's serial pins to the FPGA, without his word. Not tried on hardware (`docs/design/usb-loader.md`).
- **When something is replaced, the old thing comes out (owner, 2026-10-02: "i want it clean").** No logic, part or wire is kept "for later" once it has no job. Say what leaving it in would save, then remove it if he says so.

## v2 rules (branch `v2`)

- Everything in `hardware/sn64-v2*` is generated: `tools/build_v2_schematic.py --force` (schematics, libraries, project files), `tools/pin_plan.py` (FPGA pin map + `fpga/constraints/sn64_board.lpf`), `tools/build_v2_pcb.py --force` (placement; discards routing), `tools/prepare_route_v2.py` (fan-out, planes), `tools/apply_netclasses_v2.py`, `tools/add_plane_vias_v2.py` (run on the prepared board before routing), KiCadRoutingTools (command in `docs/design/pcb-routing.md`, v2 paths under `build/route-v2/`), `tools/finish_route_v2.py --no-import` (pours). Edit the generators, not the KiCad files, until hand layout starts.
- **The boot program runs in the ares emulator (first run 2026-10-01, ares v148; Project64 shows a black screen).** That covers the logos, the menus and controller input and nothing behind the cartridge port; it has not run on a console. Run it with `ares --system "Nintendo 64" --no-file-prompt build/n64-bootstrap/sn64_bootstrap.z64`. The menu and the logos use three picture buffers and take a new one only after the vertical interrupt (`menu_show()`): with two, ares showed the top lines wiped. Do not go back to two.
- The boot program is 163,840 bytes (147,456 from the frame lock until the stick option; 157,583 of them used on 2026-10-02, so the next addition of about 6 KB takes the file to 180,224): `ROM_ADDR_BITS = 17` (the v2 board's 256 KiB window) in `firmware/bootstrap/Makefile` and the co-simulation; it no longer fits 128 KiB.
- FPGA route for v2: `route_top.py --top board --speed 8`. The flash reader is SummerCart64's `memory_flash` unmodified; the USB core and the split-pad copy of the flash controller went with the FPGA's USB logic on 2026-10-02 (`prepare_usb_core.py` and `prepare_flash_pads.py` no longer exist).
- Owner decisions recorded 2026-09-30: **one board, never a split** (ask before any second board or module); the cartridge stands upright on top, in line with the board (TriStar-style tower with a mushroom cap that holds the cartridge), on a socket with ears screwed into the shell and sitting on the board's top edge; under 1 mA leakage into a switched-off console in USB-only use is accepted (bus switches dropped); the 2.5 V rail is an LDO; no series resistor arrays on the cartridge bus until measured.
- Local scripts only. No agents or cloud tools for this project unless the owner asks.
- Board wiring check: `hardware/sn64-v2/tools/export_board_nets.py` (KiCad's Python), then `verify_board_wiring.py` and `verify_board_wiring.py --negative`. Baseline 2026-10-02: 22 of 22 checks, 25 of 25 deliberate mistakes caught. Run both after any change to the board, the constraints or the top-level ports.
- Board rule check: from `hardware/sn64-v2`, `kicad-cli pcb drc --format json --severity-all --output validation/pcb-drc.json sn64-v2.kicad_pcb`, then `tools/report_board_v2.py` into `validation/pcb-open-connections.json`. Baseline 2026-10-02: 0 errors, 0 open connections, 438 warnings (225 silkscreen, 199 mask at the N64 edge fingers on purpose, 14 leftovers of the first routing). Any change to the board must leave it at 0 and 0.
- **What KiCad's check calls dangling can be carrying a line**: a via whose copper is the only joint between two track ends (FLASH_D2, 2026-10-02), or a track that runs on past a junction (N64_AD10, on a copy). Tidy on a copy, shorten instead of deleting, and never accept a pass after which the count of open connections has risen (`close_open_items_v2.py`, `docs/design/pcb-routing.md`). The 12 vias and 2 track ends still listed are leftovers of the first routing, left for the hand pass.
- Board simulation: after the export, `make_board_sim.py` writes the board as a netlist under `build/board-sim/`; `fpga/tools/run_game.py --board --build-dir <dir> --rom <image> --bootrom build/n64-bootstrap/sn64_bootstrap.z64` runs a game through it (3 minutes of start-up, then about 7 s a picture; start long runs detached). It must end with `DONE`; `make_board_sim.py --mutate REF.PAD=NET --out <dir>` with `run_game.py --board-dir <dir>` makes a board with a deliberate mistake, which must be refused. Run it after any change to the board, the constraints, the top-level ports or `fpga/rtl`.
- **Read a part's data sheet for its wiring rules, not only its pin numbers.** The part models in `fpga/tests/board_models.sv` carry the makers' pin numbers; the two mistakes of 2026-10-02 were rules (a level shifter byte enabled while one supply is off; an address pin tied where the sheet has no such setting). Data sheets are kept under `build/` (not committed); `pdftotext -raw` reads their tables in order.
- **Level shifters (SN74ALVC164245):** every byte's `/OE` is driven by the FPGA and pulled up to 3.3 V; never tie one on. The B side is the cartridge's switched 5 V. No A-side pin may be left open; unused channels have both pins on ground.
- A routed board is changed in place by a script that takes the pads' nets from the regenerated netlist and edits only the copper involved (`apply_enable_fix_v2.py` is the pattern; `apply_usb_loader_v2.py` for a change that moves parts and needs the router: clear, place, plane vias, lock, route, then tidy from KiCad's own report, `docs/design/pcb-routing.md`; `close_open_items_v2.py` for a ball that is boxed in: take its neighbours' nets up with it and route them together): never `build_v2_pcb.py --force` for a small change. Keep the router out from under the USB-C receptacle's body (the board has a keep-out there). KiCad 10's `PCB_VIA.GetWidth()` needs a layer argument; without it the script hangs in a dialog.
- After any change to `fpga/rtl`: `evaluate.py --mode sim`, a game run (`run_game.py` with a real image), the board run, and `route_top.py --top board --speed 8` for the timing. Baseline 2026-10-02 (without the USB logic): every clock passes, SNES master 34.6 MHz against 21.5 needed; 28,955 LUT4, 107 I/O.
- **The cartridge's pins are never loose while it has power (2026-10-02).** With the cartridge's 5 V on, the logic drives the address and strobe octets at rest whenever nobody owns the socket, and at power-off holds `/RESET` low for 1 ms before the 5 V goes (`docs/design/power-sequencer-implementation.md`). The benches check it on every clock; do not weaken those checks.

## Evidence discipline (how this repo is written)

- Keep "simulated", "static check passed" and "hardware verified" strictly separate. Do not mark a requirement accepted without the evidence the register names.
- Keep failures, negative results and red/green regression evidence (see `fpga/reports/`).
- **Do not edit `fpga/vendor/snestang/`.** Changes go through generated copies made by `fpga/tools/prepare_core.py` under `build/`. Preserve upstream licenses and notices:
  - GPL-3.0 core; SN64 HDL is GPL-3.0-or-later.
  - Sanni CC-BY-4.0.
  - SummerCart64 CERN-OHL-S-2.0.
  - usagi_ CC-BY-3.0.
  - ULX3S MIT plus a silkscreen-logo condition.
- **KiCad:** edit the native files. Never rerun `create_interface_draft.py` or `add_usb_programmer.py` with `--force`; they regenerate whole sheets.
- Never send files to PCBWay or place orders without the user's explicit go-ahead.
- **No local paths in the repository (owner, 2026-10-01; the repository is public).** KiCad netlists, check reports and notes pick up absolute paths that contain the Windows user folder. Run `python tools/scrub_local_paths.py` before committing: it rewrites that prefix to `%USERPROFILE%`, `$env:USERPROFILE` or `$HOME`, and `--check` only reports. A local pre-commit hook refuses commits that still contain it. Tool locations for this PC belong in `CLAUDE.local.md`, which is not committed.

4. Add bridge and host logic to the synthesis/route evaluation, then fix the FPGA package, pins and memory.
5. Complete the protected schematic, then PCB layout (six layers preferred to evaluate), then the FreeCAD enclosure with the side USB-C opening, then the PCBWay prototype package.
6. **PCB routing, next steps:** loosen the translator row (the congested area), finish the 75 open nets and 219 plane pads by hand in KiCad or with KiCadRoutingTools (`%USERPROFILE%\Tools\KiCadRoutingTools`, venv `%USERPROFILE%\Tools\krt-venv`; pin it with `hardware/sn64/tools/fab-pcbway.txt`), settle PCBWay annular ring (6 mil) and spacing (5 mil) against the board's 0.125 / 0.1 mm rules with the quote. Freerouting is the fallback, not the default.
